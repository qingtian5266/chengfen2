## Context

`packages/admin` 当前是 Vue 默认脚手架页面，尚未承载后台业务。后端 `packages/server/src/modules/users` 已提供用户 CRUD 接口，本次将基于这些接口落地一个轻量用户管理页。

结合你的约束：用户量小、字段少，因此本次设计刻意简化为“单页列表 + 新增/编辑/删除”，不引入分页和详情页，优先保障实现速度和可维护性。

## Goals / Non-Goals

**Goals:**
- 在 admin 中新增用户管理路由与页面，展示用户列表。
- 实现新增、编辑、删除用户主流程。
- 新增与编辑复用同一个弹框表单组件。
- 统一 API 调用与错误提示，保证交互一致性。

**Non-Goals:**
- 不实现分页器和分页交互。
- 不实现用户详情查看能力。
- 不引入复杂权限系统与高级运营功能（如批量导入导出）。
- 不重构 `server/users` 模块。

## Decisions

1. 采用单页表格展示全部用户，无分页控件。
原因：用户总量较小，分页会增加无收益的交互复杂度。
备选方案：标准分页列表。
未选原因：对当前规模过度设计。

2. 不实现独立详情查看流程。
原因：字段少且编辑前可直接回填表单，详情页价值有限。
备选方案：弹窗详情或独立详情页。
未选原因：增加维护成本，收益不明显。

3. 新增与编辑使用同一弹框组件（同一套字段和校验规则）。
原因：减少重复代码，保持字段规则一致。
备选方案：新增弹框与编辑弹框分离。
未选原因：后续字段调整容易出现双份不一致。

4. 列表加载策略使用固定参数请求 `POST /users/list`（如 `page=1,size=200`）。
原因：兼容现有后端分页接口，同时在前端实现“无分页展示”。
备选方案：调整后端新增“全量列表”接口。
未选原因：当前需求不需要新增后端契约，避免扩散改动。

5. 删除采用确认弹窗，成功后整表刷新。
原因：降低误删风险并确保前端状态与后端一致。
备选方案：本地乐观更新。
未选原因：失败回滚成本更高，首版优先稳妥。

## Risks / Trade-offs

- [用户量增长超过固定 size 阈值时列表不全] -> 将 size 提取为可配置常量，并在后续需求中切换到分页方案。
- [接口返回结构不一致导致页面报错] -> 在 API 层做统一响应适配和兜底错误提示。
- [无鉴权守卫可能带来管理操作暴露风险] -> 记录为后续安全加固项（服务端启用并校验 JWT）。

## Migration Plan

1. 在 admin 新增用户管理路由、页面与共享弹框组件。
2. 接入 users API 封装，联调列表/新增/编辑/删除四个主流程。
3. 手工回归验证主流程和异常提示。
4. 如需回滚，仅隐藏用户管理路由入口即可；后端和数据库无需迁移。
